# subagents-board 工程与交互审查

- 日期：2026-11-07
- 对象：`subagents-board` v0.4.0（`85bc447` + `d683667`）＋ 宿主新增的 `sessions.activate`（`ee39667`）
- 触发：P2-c 实机验收「功能可用，但离好用还很远」，要求不推不发版，先审查
- 范围：`agent.mjs` / `main.mjs` / `lib/*` / `ui/*` / 宿主 `activate` 链路；不含宿主既有 composer、时间线渲染
- 规模：插件 2,957 行（含测试），宿主改动 6 文件

---

## 0. 一句话结论

**数据链路是对的，问题几乎都出在「多实例 / 多进程」的边界上，以及「每秒全量重绘」这一个决定上。**
前者是静默错误（历史消失、资源泄漏、状态错配），后者是所有交互不适的公共根因（位置突变、选区丢失、焦点丢失）。

按「会不会让人误判或丢数据」排序，有 **3 条必须先修**：E1（监听器泄漏）、E2（换代丢历史）、E3（心跳与握手双调度）。

## 2. 工程缺陷详述

### E1 · RPC 回执监听器从不注销，永久泄漏 `P0`

**现象**：插件会话进程内存随时间单调增长；长时间挂着（数小时）后 tick 变慢。无任何报错。

**根因**：`pi.events.on()` 返回 disposer（`node_modules/@earendil-works/pi-coding-agent/dist/core/event-bus.d.ts:3` 明确是 `(channel, handler) => () => void`，底层 `EventEmitter.on`），但三处调用全部丢弃了返回值：

- `agent.mjs:171` 每次 RPC 请求注册 `subagents:rpc:v1:reply:<requestId>` 监听器，`finish()` 只 `clearTimeout`，不 off
- `agent.mjs:202` `subscribeEvents()` 订阅扩展事件，永不取消
- `agent.mjs:477` `pi.on('session_start', ...)` 同样

**影响量化**：心跳 5s 一次 → 每 24 小时约 17,000 个 channel + 闭包（闭包持有整个 `state`、`resolve`、`seq`）。因为 channel 名唯一，不会触发 `MaxListenersExceededWarning`——**完全静默**。stale 换代时旧实例的定时器停了，但已注册的 handler 仍挂在总线上，每个 handler 还持有一份旧 `state` 快照（含全部 lineages），等于每次换代都泄漏一整份历史。

**修法**：

```js
// request() 内
const off = pi.events.on(channel, handler)
const finish = (result) => { if (settled) return; settled = true; clearTimeout(timer); off(); resolve(result) }
```

`subscribeEvents` 把 disposer 收进 `disposers[]`，`stopTimers()` / `markStale` 时统一执行。注意 `EventBus` 没有 `off` 导出，只能靠返回值。

**验证**：注入 1000 次 `request()` 后断言 `emitter.listenerCount(channel) === 0`；或连续 10 分钟跑心跳，断言 `process.memoryUsage().heapUsed` 斜率 ≈ 0。

### E2 · 实例换代后历史链消失，并且误报「没有子代理运行」 `P0`

**现象**：在两个会话间来回切，或重启应用后回到原会话，右栏从「三张卡」变成「这个会话最近没有子代理运行」，而实际上那些 run 有记录、文件还在。切回去也不需要新派 run，只要等下一次事件才会重新出现。

**根因**：两层都按「单实例」假设写的。

1. `agent.mjs:53` 每次工厂调用 `createState()` 从空白开始。扩展换代（`newSession` / `fork` / `switchSession` / reload）是常态，新实例不知道上一代写过什么。
2. `main.mjs:84` `latestForSession()`（`live-store.mjs:103`）只取 `startedAt` 最大的**一份**文件。新实例的文件 `lineages: []`，于是最新一份就是空的，旧的那份被完全忽略。

于是 `stateFor()` 返回 `degrade: ok` + `lineages: []` → UI 走 `data.degrade?.kind === 'ok'` 分支，显示「这个会话最近没有子代理运行」（`ui/app.js:430`）。**这是最糟的一类错误：不是缺数据，而是用确定语气说了一个假结论。**

同一个 bug 还让 `activeCount` 归零——后台明明还有子代理在跑，面板说「0 个在跑」。

**修法（推荐在 main 侧合并，agent 侧不碰）**：

- `readLiveFiles` 结果按 `sessionKey` 分组，按 `startedAt` **升序**合并 `lineages`，`runId` 去重（后写的覆盖先写的字段）；
- `source` 只取最新实例的（数据源健康度必须反映「现在」）；
- 合并时给来自旧实例的段打 `origin: 'previous-instance'` 或增加 `instance` 字段，UI 上可以标「历史」，也便于诊断；
- 空态文案改成「本实例启动后还没有子代理运行记录」——**只有真的没有任何文件时才说「没有运行」**。

**代价**：一次多读几份文件。配合 E6 的缓存后不是问题。

**验证**：单测构造「同 sessionKey 两份文件，旧的 3 段、新的 0 段」，断言 `lineages.length === 3` 且 `activeCount` 正确。

### E3 · 握手失败时心跳仍在跑，每 5s 一个注定超时的请求 `P0`

**现象**：没装 / 没启用 pi-subagents 时，每个会话进程持续静默空转；宿主日志里 `status 无回复` 周期性出现；CPU 与内存缓慢增长。

**根因**：`agent.mjs:515-518` 无条件同时启动两条调度：

```js
void handshake('boot')                    // 失败会自己排 retry（2s→5s→10s→20s）
restartHeartbeat(HEARTBEAT_PUSH_MS)       // 也是无条件，5s 一次 readStatus
```

`readStatus`（`agent.mjs:258`）在 `mode === 'none'` 时没有任何停止条件——降级逻辑只在 `mode === 'push'` 触发（`agent.mjs:271`），所以 mode 为 none 时永远不降级、也永远不停，每个 5s 发一次 `status`，8s 后超时，叠加 E1 再泄漏一个监听器。

**修法**：

- `restartHeartbeat` 只在 `state.source.rpc === true` 时调用（握手成功后由 `handshake` 负责，boot 时不要盲启）；
- `readStatus` 的失败分支加：`if (state.source.mode === 'none') { 停心跳 }`，把节奏交回 `handshakeTimer`；
- 心跳与握手重试不要并存——同一时刻只应有一个「谁的错」。

**验证**：假总线永不回复，断言 60s 内 `status` 请求数 === 0（只有 ping），且 `ping` 间隔单调递增。

### E4 · `mergeChildren` 按数组位置归位，顺序一变就静默错配 `P1`

**根因**：`lineage.mjs:436-460`。实测 pi-subagents 的 status children 不带 `index`，于是改成「按 incoming 数组位置归位」。这修好了刷屏（原来是 `byIndex.size` 兜底每次都追加），但把正确性押在「扩展每次都按同样顺序返回同一批 child」上。

**风险场景**：扩展某次升级后按状态/完成度排序，或 run 中途新增一个 child 插在前面——位置错配，于是 **A 行的模型/状态显示在 B 行上**。路径因为只在 `incoming.length === 1` 时补，不会错配，所以错误更隐蔽：看起来一切正常，只是信息是别人的。

**修法**：身份优先，位置兜底。

1. 有 `index` 用 `index`；
2. 没有时用 `(agent, model, thinking)` 做身份键匹配已有条目；
3. 匹配不到才按位置取新的；
4. 匹配成功但位置不同时，保留身份匹配结果（并把 `index` 更新为当前位置，便于排序稳定）。

**验证**：单测「incoming 顺序颠倒」→ 断言各条目字段仍与自身 agent 对应。

### E5 · 命令 5s 死线与回执语义不自洽 `P1`

**根因**：`main.mjs:226-249` 等 5s，超时删文件并返回「命令没能送达」；`agent.mjs:434` 用同一个 `REPLY_WAIT_MS` 判过期。双端同口径确实挡住了「等很久之后突然插进去」的大窗口，但留下了两个小窗口：

1. **认领后执行前**：agent 在 4.9s 通过过期检查，5.2s 才发出 RPC 并成功 → 子代理收到了，用户看到的是「没能送达」。窗口 = 一次 `JSON.parse` + emit，通常 <10ms，GC 或慢盘可到数百 ms。
2. **main 先超时、agent 后写结果**：结果文件没人读，只能等 TTL 清；用户永远不知道其实成了。

第 2 类更麻烦：它是「不可解释行为」的温床——用户会复述成「有时候点两次才生效」。

**修法（按性价比排序）**：

- **先改文案（10 分钟，收益最大）**：超时不再说「没能送达」，改说「没等到回执，可能没送到，也可能它已经收到了——切回那个会话看看状态再说」。把「不确定」如实说出来，比给一个错误的确定结论好。
- **加显式取消**：main 超时后写 `cmd-cancel/<id>.json`，agent 在 emit 前检查一次；能消掉窗口 1。
- **加追认**：agent 若在 result 里带 `at` 且 main 已超时，下一次 `getState` 时把该 id 标为「已送达（迟到回执）」，UI 上以弱提示呈现。

不建议把窗口拉长到 30s——那只是把不确定期变长。

### E6 · 读盘无缓存，每秒全目录解析两次 `P1`

**根因**：

- `main.mjs:84` `latestForSession` → `readLiveFiles` 读目录下**所有** `.json` 并 `JSON.parse` 全文（`live-store.mjs:70-93`）；
- `main.mjs:90-97` lineages 为空时再跑一次 `findOwnerOf`，**又**一次全目录；
- `main.mjs:293` `sweepInbox` 每 5s 又一次全目录；
- UI 每秒 `getState` → 上面第一、二步。

**影响**：live 文件按会话累积（7 天保留，见 E12），100 份 × 平均 20KB = 2MB；面板开着就是 2–4 MB/s 的解析 + 大量小文件 IO。Windows 上还会被实时防护放大。

**修法**：

1. 进程内缓存 `Map<file, { mtimeMs, size, state }>`，`stat` 后未变则复用（`stat` 比 `readFile` 便宜一个量级）；
2. `latestForSession` 先用文件名前缀筛（文件名已含 sessionKey：`<key>-<pid>-<startedAt>.json`），只解析候选；
3. `findOwnerOf` 结果按 `(target, liveDirMtime)` 缓存 30s——它只在预览子会话时用。

**验证**：基准 1000 份 × 20KB，`getState` 冷启 < 30ms、热路径 < 5ms。

### E7 · 数据自愈放在读侧，缺 schema 迁移 `P1`

**根因**：`lineage.mjs:490-522` `sanitizeChildren` 在 `listLineages()`（`lineage.mjs:544`）里对每个 segment 跑一遍三层启发式——这是为了修「按 `byIndex.size` 兜底」时期攒出来的重复条目（实测 123 条）。数据本身没被修正，靠每次读的时候猜。

**问题**：

- 每秒一次（UI tick）对全量数据跑三段 O(n²) 合并（`rooted.find`）；
- 启发式的第 2 层「identity 全同即吸收」在「同一 agent 并发多 child 且状态全同」时会误吸收（已被测试抓到过一次，所以范围收窄到 `withFile`）；
- 一旦线上数据被启发式误判，就永久错——因为错的是内存视图，下次读还错。

**修法**：`schema: 1` → `schema: 2`，写侧迁移：

- 读到 `schema < 2` 时跑一次清洗，把结果**写回**（agent 侧 `flushNow` 或 main 侧一次重写），并置 `schema: 2`；
- 之后的读路径只剩「归一化」（`normalizeModelThinking`，O(n)），不再猜；
- 迁移代码留在 `lib/migrate.mjs`，带单测（输入旧污染样本 → 输出收敛后样本）。

### E8 · 常量重复定义、与使用处脱钩 `P1`

三处具体的「谎言」：

1. `lib/cmd-queue.mjs:21,23` 导出 `CMD_TTL_MS` / `RESULT_TTL_MS`，但 `main.mjs:170-174` 清理时**硬编码** `30_000 / 30_000 / 120_000`。改常量不会生效——这比不导出更糟，因为代码在暗示一个不存在的契约。
2. `TERMINAL_STATES`（`lineage.mjs:52`）与 `TERMINAL`（`inbox-watch.mjs:16`）各写一份，注释还自陈「这里不 import，避免 main 侧多一条模块依赖」——为省一条 import 复制语义，是最不划算的交易：新增一个终态时漏改一处，表现为「面板已结束但信箱还在通知」。
3. `STATE_TEXT` 在 `ui/app.js:81` 与 `inbox-watch.mjs:18` 各一份（后者少了 `stopping`，所以停止中的信箱标题会显示英文原文）。

**修法**：`lib/constants.mjs` 只放纯常量（无 IO、无副作用），两边都 import。`ui/` 用同一份（面板是 ES module，能直接 import）。

### E9 · 死接口与死代码 `P2`

- `getDiagnostics`（`main.mjs:319`）生产代码无人调用，只有测试；UI 的「诊断」折叠区直接用 `getState().source`。
- `parseLiveName`（`live-store.mjs:52`）只有测试用。

**修法**：二选一，别留着占位。

- `getDiagnostics` **接通**：它比 `source` 多了 `liveDir` / `mtimeMs` / 原始 `state`，正好补 S7 的「开发者级诊断」。接通成本比删掉更低。
- `parseLiveName` 删掉（命名解析已在 `latestForSession` 内联完成）。

### E10 · `sessions.activate` 未 bind `P2`

`main.mjs:338`：

```js
const jump = typeof sessions.activate === 'function' ? sessions.activate : sessions.reveal.bind(sessions)
```

`reveal` 分支 bind 了，`activate` 分支没有。当前宿主实现是箭头函数所以不出错，但这是「依赖实现细节」的写法：宿主一旦改成依赖 `this` 的方法，`reveal` 正常、`activate` 崩。统一 `bind(sessions)`。

### E11 · `markStale` 靠错误文案正则匹配 `P2`

`agent.mjs:135`：`/stale after session replacement/`。上游改文案 → 检测失效 → 旧实例继续每 5s 请求，每次 emit 抛错（被 `catch` 吞成 `emit_failed`），日志被刷、`lastError` 一直变。

**修法**：优先判 `error?.code`；正则放宽到 `/stale/i`；再加一条兜底——`emit` 连续失败 N 次（与 `MAX_STATUS_FAILURES` 复用）也判定换代并 `stopTimers()`。

### E12 · 单会话 live 文件只增不减 `P2`

`state.lineages` 只增：每个 run 一段，resume 再加一段，永不裁剪。7 天清理按文件 mtime，而活跃会话的文件一直在写 → 永不触发。后果是 E6 的读放大与 S1 的重绘成本随时间线性变差。

**修法**：写侧保留策略（最近 N 条终态链，或最近 7 天按 `endedAt`），并在 `state` 里加 `trimmed: n`，诊断区显示「已隐藏 n 条历史」。不要静默丢——用户会以为是 bug。

---

### E13 · `agent.mjs` 四职责合一 `P2`

一个工厂函数 559 行，闭包共享 12 个可变变量（`sessionFile / liveFile / disposed / stale / seq / statusFailures / dirty / readyEvents / 4 个 timer / subscribed`），同时管生命周期、握手退避、事件订阅、命令队列、会话 hook。

**修法（真想长期维护才做）**：拆 `rpc-client.mjs`（`request` + `handshake` + 退避表，暴露 `onModeChange`）、`command-runner.mjs`（`startCommands/scanCommands/runCommand`）、`heartbeat` 内联进 rpc-client。注意：agent 侧**不能**用 `?v=` 动态 import（只有 main 侧热重载），拆文件时保持静态 import，并在文件头注明「改这些要新开会话才生效」。

### E14 · 插件自身没有对外可观测性 `P2`

排查「为什么没数据」现在只能：看宿主日志里的 `ctx.log`，或者让用户读诊断区那一行 `lastError`。插件自己记录的握手次数、订阅到的事件名、命令收发的历史，全都不在 UI 里。

**修法**：`state.diagnostics = { recent: Ring(20) }`，写关键节点（握手成功/失败、订阅事件数、命令认领、命令结果、stale）。诊断区展示，`getDiagnostics` 正好一起接通（见 E9）。环形缓冲必须定长，否则就是 E12 的重演。

### E15 · 测试缺口 `P1`

现状 75 例全绿，纯函数覆盖很好（lineage / cmd-queue / inbox-watch / degrade / live-store / main / agent）。缺三类：

### S1 · 每秒全量 `innerHTML` 重绘（最高杠杆） `P1`

**用户看到的**：

- Tab 到「插话」按钮 → 1 秒后焦点回到 body

**修法（按投入递增）**：

1. **最小改动**：先算 `nextHTML`，与 `lastHTML` 相同则直接 return（数据没变时不做任何 DOM 操作）。tick 1s 一次但绝大多数帧数据不变，能挡掉 90% 的重绘。

3. **长期**：`preact`/`lit` 之类，但外部插件不宜带框架，前两步足够。

顺带：滚动策略要区分「贴底」与「在翻历史」——只在用户贴底时保持贴底，否则锁定视口锚点元素。

## 5. 用户两条新诉求的落点

### U4 · 去掉绿色横幅

**做法**：删 `setActionResult({ tone: 'ok' })` 这条路径。

- `openSession` 成功不再提示。理由：会话真的切走了，这是比横幅更强的反馈；留在原地面板上「已打开」反而是噪音。
- 保留 `warn` / `error`（「会话文件已不存在」「打开失败：…」）——这类信息用户无法从界面推断。
- 「正在打开…」也别做——1s 内就完成，闪一下反而像卡顿；若确实慢（>300ms）再显示。

改动量：`ui/app.js` 三处 + `style.css` 的 `.result-ok` 删除。**10 分钟。**

### U3 · 插话复用输入框

> **本节第一版写错了，已按 2026-11-07 17:56 用户指正重写。** 原文说「输入框是宿主锁的，与插件无关」——把责任推给了宿主。用户指出：实验阶段输入框本来没锁，是后来才锁上的；只要它是一个单独的会话，就具备输入能力。核查后**用户是对的**。

**事实链（四步，都能在代码里指到）**

1. **锁定判据原本不是「预览」，而是「worker 冲突」**（`ad8a36d` 时的实现）：

```ts
isSessionPreviewComposeLocked(viewSessionFile, workerSessionFile, workerStatus) {
  return isViewingDifferentSessionThanWorker(viewSessionFile, workerSessionFile) && workerStatus === 'running'
}
```

即：只有「你在看 A、worker 绑在 B、且 B 正在跑」时才锁。**你在看的会话就是 worker 绑定的那个，输入框就是可用的**——这正是用户记忆里的实验期状态。

2. **现在的实现换掉了判据**（`session-worker-sync.ts:83`）：

```ts
isSessionPreviewComposeLocked(viewSessionFile, _workerSessionFile, _workerStatus, readOnlyPreview = false) {
  return readOnlyPreview && !!viewSessionFile
}
```

两个 worker 参数被废弃成下划线——判据从「有没有 worker 冲突」变成「是不是预览」。

3. **`readOnlyPreview` 来自 `bind: false`**。`revealSessionPreview`（`src/renderer/src/lib/reveal-session.ts`）显式传：

```ts
await ipcClient.invoke('session.prepare', { sessionFile: target, bind: false })
await previewSessionInPlace(...)   // → openExistingSessionView(..., bindWorker = false)
```

而 `bind` 的默认值是 **true**（`src/main/ipc/handlers/session.ts:141`：`if (req.bind !== false) setPendingWorkerSessionFile(sessionFile)`）。也就是说：**绑 worker 是默认行为，不绑是这次调用特意要求的。**

4. **`session.prepare` 本来就能处理任意会话文件**（`src/main/session-prepare.ts:63`）：只要首行有 meta，就返回 `sessionId + cwd`，**不看它在不在侧栏列表里**。更关键的是它还专门写了 `parseDerivedChildSessionLocator`，去识别 `<父stem>/<runId>/run-<i>/session.jsonl` 这种子会话路径、再到 `listSessions` 里匹配适配器注册过的子会话——**宿主早就准备好了「子会话是一个正式会话」这件事。**

**结论**：能力一直在。是我用 `bind: false` 把它关掉，然后为了给「关掉」找理由，又把锁的判据改成「预览即锁」。`revealSessionPreview` 的注释写着「插件能命令宿主『看一眼』，不能命令宿主『接管』」——这是我自己定的克制，但我把「插件不该擅自接管」执行成了「用户也不能接管」。这两件事不一样：不该做的是**插件自动**跳到可写会话（会打断用户正在编辑的内容）；用户**主动点击卡片**进去，本来就该拿到一个正常会话。

**正确模型**：会话可写性只有一个开关——**有没有绑 worker**。绑了输入框就可用，不需要额外「解锁」。

**按 run 状态分流**：

| 目标会话 | 打开方式 | 输入框 | 理由 |
|---|---|---|---|
| run 已终态 | `prepare { bind: true }` → `switchSessionInPlace` | **可用** | 它就是一个普通历史会话，和从侧栏点开没有区别；可以直接接着聊 |
| run 进行中 | 保持预览（不绑 worker） | **不能用宿主 prompt 发** | 子代理进程持有自己的 SessionManager 在 append 同一份会话；宿主再绑一个 worker 发言会写出第二条父链，且对方上下文里没有你这句话 |

> **更正：不是「双写坏文件」。** 第一版写成「双写同一 jsonl」，暗示文件会被写坏。核过 pi 的存储实现后，这个说法不成立：
> - `SessionManager._persist` 加载已有文件时 `flushed = true`（`session-manager.js:690`），之后一律 `appendFileSync` 单行追加；整份重写只发生在新会话首次落盘（`openSync(file, 'wx')`，文件已存在会直接抛错）。
> - 真正的后果是**两条父链分叉**：两个进程各自维护内存里的 `leafId`，各自 append 的行带各自的 `parentId`。下次加载按 parentId 回溯，只有最后写的那条链可见，另一条变孤儿分支。
> - 更致命的是**上下文互不可见**：子代理进程的输入上下文里没有宿主插入的那句，它不会照着调整——你只是往文件里写了一行它看不见的字。
> - 所以「运行中发言」坏的不是文件，是「你以为在跟它说话，其实没有」。**要实现这件事，机制必须是 steer**（投进它正在跑的那个循环），而不是让宿主另起一个循环。

**进程模型实证（2026-11-07 18:10 补，回答「不同会话是不是同一个 pi 进程」）**

是**不同进程**。宿主不共用一个 pi 进程管所有会话：

- 每个会话一个 Electron `utilityProcess`：`forkWorkerForCwd` 里 `utilityProcess.fork(resolveUtilityEntry('worker.mjs'))`（`worker-manager-pool.ts:399`），独立 pid、独立堆。
- 池 key 就是会话文件绝对路径：`normalizeSessionKey(sessionFile)`（`worker-session-key.ts`），`ensureSessionWorkerUnlocked` 先 `this.pool.get(sk)`，命中即复用，否则 fork 新进程。
- 容量默认 4（`config-store.ts:148 maxSessionWorkers: 4`），池满先驱逐 idle，还不行就抛 `Worker pool full (N running sessions)`（`worker-manager-pool.ts:528`）；另有 15 分钟空闲回收（`sessionWorkerIdleTimeoutMinutes`）。
- 一个 worker 内部只有一个当前会话（`st.session` 单例）。切会话走 `switchOrLoadSession`，且正在跑 turn 时会被 `WORKER_AGENT_BUSY` 拒掉（`worker-handlers-session.ts:200`）。

同进程复用只有三种情形，都不影响上面的结论：① prewarm 的空 workspace worker 被认领给某会话（`findReusableSlotForSession`，要求 `!agentTurnActive` 且没有 `sessionFile`）；② 显式切会话——`loadSession` 成功后才把 `poolKey` 改到新会话（注释里写的是 commit point）；③ 驱逐后重建。

所以三件事要分开：

| 场景 | 写同一份 jsonl 的进程数 |
|---|---|
| 普通会话：你打字 + agent 说话 | **1**（同一个 agent 循环，输入是 steer/queued 事件，同一份 `SessionManager` 顺序 append） |
| 子代理后台 run | 1（pi-subagents `spawn` 的独立子进程，`--no-session` + 自己指定 session 路径） |
| 运行中的子会话被你用绑 worker 的方式打开并发言 | **2**（子代理进程 + 宿主新 fork 的 worker） |
| 终态子会话被你打开 | 1（子代理进程已退出，只剩宿主 worker） |

「双写」的成因不是「会话多」，而是「同一份 jsonl 被两个进程各持一个 `SessionManager`」。这也解释了用户为什么会合理质疑——普通会话里确实有两个主体在动，但它们在一支笔上轮流写。

**由此补一条判据**：`writeable` 不能按「上一段是否终态」算。resume 会起**新进程**写同一份文件，上一段终态而链尾正在跑的情况很常见。判据必须是「这条 resume 链**当前**没有活跃 run」（取链尾状态），否则会在 resume 刚起来的窗口里误开写。

**还有个容量问题**：终态绑定会额外占一个 worker 名额。用户已经开着 4 个会话时，打开子会话会驱逐一个 idle worker（或直接报满）。这不是错误，但要在交互上能解释——否则表现为「点卡片进去，另一个会话被关掉了」。

这样 U3 的「用输入框插话」在终态场景**不需要任何新机制**——打开即可用；只有「运行中插话」才需要面板通道。

**落地改动（两处，都在宿主）**

1. `activatePluginSession`（`src/renderer/src/lib/activate-plugin-session.ts:28-40`）删掉「不在 `store.sessions` 就退化为预览」这层兜底：改为先 `session.prepare { bind: true }`，拿到 `sessionId` 就走 `switchSessionInPlace(sessionId, file)`；`prepare` 失败（文件不存在 / 不是会话文件）才回退预览。现在的 `store.sessions.find()` 前置判断是本末倒置——**侧栏有没有它，和它能不能被打开，是两件事**。
2. 「运行中不绑」这条判断需要知道 run 状态。插件有 live 数据，应该由调用方（插件的 `openSession`）传 `writeable: false`，**别让宿主去猜 pi-subagents 的状态**。

**验收**

- 派一个 run 跑完 → 点卡片进去 → 输入框可用 → 直接发一句 → 能收到回复（不需要回主会话点 resume）
- 派一个长 run → 运行中点卡片 → 输入框禁用、面板插话有效
- 两种情况下「返回主会话」都在，且回去后可写

**风险**：终态绑定没有副作用——worker 接管一段已经写完的 jsonl，与打开任意历史会话等价，只有一个写者。
运行中绑定「只看不发」也不坏文件，但显示会滞后（worker 的 `fileEntries` 是加载时的快照，看不见对方后续 append），所以实时性仍然要靠 tail 增量读（H3）。**运行中要「说话」，只能走 steer。**

**面板侧仍要做的（与上面解耦）**：坞做成主输入框同款——底部固定条、单行自适应、`Enter` 发送 / `Shift+Enter` 换行、发送后原地一行回执（不做绿条）。这部分只影响「运行中插话」，与终态可写无关。

**如果将来真要在运行中复用主输入框**（而不是面板坞），形态是明确的：宿主给预览态一条「发送 → 插件 steer」的通道，输入框保持可用，但发送落点不是 `session.prompt` 而是插件的命令队列。这不破坏「只读预览」的语义——那段会话本来就不是给你写历史的，输入框在这个上下文里唯一的含义就是「跟正在跑的那个子代理说话」。**不要**让它落到宿主 worker 的 prompt：那会另起一个循环，写出第二条父链，而且对方根本看不到。

**另外一条必改**：**停止不应该和插话共用一个坞**。停止不需要文本输入，却占掉整个底部输入区、还把输入框换掉，这是「交互一般」的直接来源。停止应改为卡片内就地二次确认（按钮变「确认停止」+ 3 秒回退），不打断阅读。
